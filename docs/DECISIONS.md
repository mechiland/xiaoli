### A2. DeepSeek instead of Anthropic
SPEC §4 and §12 say Anthropic; PLAN overrides with DeepSeek `deepseek-flash`. Facts from api-docs.deepseek.com (2026-09-15):
- OpenAI-compatible base URL `https://api.deepseek.com` (`/chat/completions`); Anthropic-compatible at `/anthropic` (not used).
- Models: `deepseek-flash` (DeepSeek-V4.1-Flash), `deepseek-v4-pro`. 1M context, 384K max output.
- Flash price / 1M tokens: input cache hit $0.003–0.006, cache miss $0.15–0.30, output $0.60–1.20 (peak = 01:00–04:00 and 06:00–10:00 UTC Mon–Fri is 2× off-peak).
- JSON output: `response_format: {"type":"json_object"}`; prompt must contain the word "json" and an example; API may return empty content (treat as retryable); set `max_tokens` so JSON isn't truncated.
- **Thinking mode is the default for deepseek-flash.** OpenAI format toggle: `thinking: {type: "enabled"|"disabled"}` (in `extra_body` for SDKs; plain field for raw fetch). In thinking mode `temperature`, `presence_penalty`, `frequency_penalty` are accepted but ignored; `top_p` floored at 0.95; reasoning returned in `reasoning_content`.
- Temperature guidance table: coding/math 0.0, data cleaning/analysis 1.0, conversation/translation 1.3, creative 1.5; default 1.0.
- **Decision**: PLAN requires "temperature 取文档建议的最低可用值" → `temperature: 0` with `thinking: {type: "disabled"}` (so temperature takes effect and output tokens aren't spent on reasoning). The llm builder must confirm with ≤ 5 small live calls that non-thinking mode + json_object works for deepseek-flash and record the result here; if thinking mode yields materially better eval scores, extract may enable it via `LLM_THINKING=enabled` with a prompt version bump and recorded comparison.
- Direct `fetch` implementation (no OpenAI SDK) to keep the Worker bundle small.
- Secrets: `DEEPSEEK_API_KEY` in `.env.local` (Next dev) and must be mirrored into `.dev.vars` for wrangler/getPlatformProxy contexts; both gitignored. Deploy: `wrangler secret put`.

### A3. OpenNext + Next 16 caveats
- `next.config.ts` calls `initOpenNextCloudflareForDev()`; bindings via `getCloudflareContext()` (sync in route handlers/RSC; `{async:true}` for static generation — all our pages are dynamic, so sync is fine).
- **No `proxy.ts` / `middleware.ts`.** Next 16 renamed middleware to `proxy.ts` and it runs on the Node runtime; OpenNext Cloudflare lists "Node Middleware" as not supported. Auth gating is therefore done in `app/(app)/layout.tsx` (server-side `getAuth(env).api.getSession({ headers: await headers() })` → `redirect('/sign-in')`) and in Hono session middleware for `/api/*`. SPEC M0's "未登录访问 /people 跳转登录页" is tested as "unauthenticated `/` and `/p/:id` redirect to `/sign-in`".
- No `export const runtime = 'edge'` anywhere.
- DB clients per request (OpenNext docs): `getDb()` wrapped in React `cache()`; no module-level db/auth singletons.
- `.dev.vars` needs `NEXTJS_ENV=development`.
- Worker size limit 3 MiB (free) / 10 MiB (paid) gzip — deploy checks. Risk: lunar-typescript + pinyin-pro dictionaries in the server bundle. Mitigation: pinyin sort key computed on write (`persons.label_sort`) so pinyin-pro can be client/seed-only if needed; deploy critic measures.
- Next 16 dev uses Turbopack by default; OpenNext docs list Turbopack as supported. If `next build` output misbehaves with OpenNext, core/deploy may use `next build --webpack`; record here.

### A4. Better Auth on D1
- `getAuth(env)` per request (SPEC §4). Uses `drizzleAdapter(drizzle(env.DB), { provider: 'sqlite', schema })` from `@better-auth/drizzle-adapter` rather than Better Auth 1.5's native D1 auto-detection, so auth tables live in the same Drizzle schema and one `drizzle-kit generate` → `wrangler d1 migrations apply` pipeline (SPEC §4 says Drizzle adapter + sqlite provider).
- D1 has no interactive transactions; Better Auth uses `batch()` for D1. Our own multi-statement writes use `db.batch()` with idempotent status guards (ARCHITECTURE §4.2).
- Schema generation needs a static config: `server/auth.config.ts` (no env access) consumed by `npx auth@1.7.5 generate --adapter drizzle --dialect sqlite`.
- Known local pitfall: multiple Drizzle wrappers around the same local D1 binding in one request can hit SQLite WAL write locks — create one db per request and pass it to `getAuth`.
- `nextCookies()` plugin not needed (sign-in/up via client `authClient` → `/api/auth/*`), unless core uses server actions for auth.

### A5. SPEC/PLAN conflicts and resolutions
1. **SPEC M0 "侧边导航" and `/people`** vs SPEC §9.2 "不做侧边栏" and routes `/p/:id`. → §9.2 wins (it's the detailed IA). No sidebar; top bar only. No `/people` route. M0 acceptance test uses `/` and `/p/:id`.
2. **Anthropic → DeepSeek** (A2). `server/llm/` has a DeepSeek implementation only; adapter interface is provider-agnostic.
3. **Directory structure SPEC §5 vs module ownership.** SPEC lists `server/routes/{imports,people,chats,claims,review,home,search}`; to give disjoint ownership we split into per-module router files (ARCHITECTURE §1 table): e.g. `people.ts` (person) vs `people-actions.ts` (review: merge/split/manual add), `chats-list.ts` (import) vs `chats.ts` (chat), `imports-review.ts` (review). There is no `claims` router — claim actions go through `/api/review/claim/:id` and `/api/people/:id/claims`.
4. **`prompts/` ownership**: SPEC §5 puts prompts at repo root `prompts/extract.v1.md`; owned by extract. Eval judge prompt lives under `prompts/judge/` (eval-synthetic) to keep prompts/ single-owner.
5. **Gold path split and gold authorship**: PLAN says `eval/gold/<文件名>.json`. → `eval/gold/synthetic/<zip>.json` (committed) and `eval/gold/real/<zip>.json` (gitignored). Reason: a single dir can't be partly gitignored by file name reliably, and real gold contains real names. **Who writes gold**: both synthetic and real gold are written by the independent **annotator** role (ARCHITECTURE §1.16, §7.6), NOT by eval-synthetic (which runs the eval and sees pipeline output). eval-synthetic only generates ZIPs plus `fixtures/synthetic/<zip>.intent.json` (planted traps), which the annotator may read only after freezing. This matches PLAN §2 (blind, item-by-item annotation); what we add beyond PLAN is the freeze mechanism (revised round 3, A7 #3): one committed, append-only `eval/gold/LOCK.json` with a version history per zip (real zips keyed by `real-<16 hex of ZIP sha256>`, hashes only), `goldSha256` in every EvalReport. Gates fail when a gold file differs from the last LOCK version, when any version after the first lacks a matching `gold-change: <lockKey> <sha12>` line under `## annotator` in this file, or when the working LOCK is not an append of the committed one.
6. **Report path split**: PLAN `eval/reports/<时间戳>.json` is kept for the combined **aggregate-only** report (real zip names anonymized as real-1..n); per-item detail for real data under `eval/reports/real/` (gitignored); synthetic detail under `eval/reports/synthetic/`.
7. **PLAN M5 error taxonomy** has 5 classes; PLAN §2 lists 6 (adds 证据引用了窗口外或不存在的消息). → Use PLAN §2's 6 + `other`.
8. **ReviewAction enum**: SPEC §7 `accept|reject|edit|merge|split|supersede`; SPEC §9.5 has a hard "删除" for confirmed claims (not into history). → add `delete`.
9. **"改写" history**: SPEC §9.5 says edited original moves to 历史; §9.9 says edit in import-result confirms with edited content. → person page edit of a confirmed claim creates new confirmed claim + old row `superseded` with `status_reason='edited'`; import-result edit of a proposed claim updates in place and confirms (reviewLog keeps `before`), no history row (it was never confirmed).
10. **"已过时"** without replacement: SPEC status enum has no `outdated`. → status `superseded` + `status_reason='outdated'`, `valid_to` set to today (YYYY-MM-DD).
11. **handles unique `(ownerId, kind, value, chatId)`** with nullable chatId: SQLite treats NULLs as distinct → unique expression index on `ifnull(chat_id, 0)`.
12. **messages unique `(chatId, seq)`** + LCS reordering: seq assigned with gaps of 1024; renumbering is a two-phase batch. Prompts use per-window local seq numbers, mapped back to message ids — so "evidence seq in window" validation uses local indices.
13. **Importing duplicates**: SPEC 9.7 checks duplicate in step 1 (before upload). → added `POST /api/imports/check {sha256}`; `POST /api/imports` still enforces uniqueness (409). An import left in status `mapping` does not count as a duplicate (A7 #2).
14. **`import_messages` table** added (not in SPEC §7) to show per-import message ranges on the chat page and support delete semantics; **`claim_mentions`**, **`user_settings`**, **`llm_calls`** added. `imports.chatId` nullable (import exists before mapping).
15. **messages.sender_name** added: SPEC delete-person says "sender 置为未知" but chat page should still show the raw display name for unlinked senders (§9.10). We keep the raw name; the person link is removed.
16. **Retries**: PLAN "重试最多 2 次" = up to 3 attempts per window total, counted across `jobs/next` calls (job-level), not inside one request (30 s budget).
17. **Budgets on dev server** (revised round 2): one scenario `_smoke/perf-budgets`, one statistic: 4 sequential loads, first discarded, **median of loads 2–4** ≤ 300 ms (document TTFB and `Server-Timing` of the page's API). The gate runs against `next dev` on :3000. Production-like confirmation uses `pnpm preview:prod` = `opennextjs-cloudflare build && opennextjs-cloudflare preview` (OpenNext CLI docs, checked 2026-09-15: preview populates the local cache and serves the built worker through `wrangler dev`, i.e. workerd with the local `.wrangler/state` bindings; wrangler dev default port 8787). `next start` was dropped: `initOpenNextCloudflareForDev` targets `next dev`, so `next start` would not get D1/R2 bindings. Preview is integrator-only (second process, memory-tight machine). If dev fails only from dev overhead while preview passes, record both logs here; the critic may accept.
18. **Eval gating with tiny real samples**: the three real ZIPs contain ~136 messages total (counts only). Precision/recall on real data will have very few items (likely < 30 gold claims), so a single error moves precision by several points. Gates are evaluated on real and synthetic separately and both must pass; synthetic ZIPs must be substantially larger and cover the transactional/sensitive/inference traps. Gold (real and synthetic) is frozen after annotation (A5 #5); no edits to raise scores, per PLAN.
19. **STATUS.json modules**: PLAN lists 13 modules; we add `verify-seed` and `eval-synthetic` infra modules. The annotator is a role without code or critic, so it has no STATUS entry.
20. **Ownership moves made for the wave rule** (round 2): a module may only depend on modules of the same or an earlier wave. So: `PersonPicker` → search (wave 2; PLAN lists it nowhere, SPEC §9.7 needs it in the wave-2 import overlay); Evidence component → review (wave 2; PLAN puts "证据组件" under person, wave 3, but review owns the evidence API and both wave-3 pages consume the component); `POST /api/people` → review; `GET /api/people?index=pinyin` + `listPeopleIndex` → search; `GET/PATCH /api/settings` → core (read by the wave-2 import overlay and wave-3 home/welcome/import-result). Core ships placeholder pages and components so wave-2 flows never hit a 404. Deviation from PLAN §1's list, which assigns 证据组件 to person.
21. **`/welcome` route**: not in SPEC §9.2's route list. SPEC §9.12 requires a single-page onboarding right after sign-up, so we add `/welcome` (home module). Core's sign-up page redirects there after success; `(app)/layout` does not force it (SPEC says it can be skipped). Both save and skip set `onboardedAt`.
22. **invalid-evidence gate reading**: PLAN §4 "证据引用无效消息：0". Extract's validation drops items whose evidence is outside the window, so gating the pipeline's own post-filter count would always pass. We gate `invalidEvidencePost`, **recomputed independently by the harness** from the parsed export and each item's window range (so a bug in the filter, id mapping or persistence still fails the gate). This follows the product reading: no stored item points at an invalid message. The raw model rate before filtering (`invalidEvidencePreRate`) is reported, with a warning above 5%, and not gated: dropped items already lower recall, which is gated.
23. **Strict vs lenient claim matching**: judge verdicts `same | less_specific | different` (an added unsupported detail = `different`). The precision gate (≥ 0.85) uses lenient (same + less_specific), because a vaguer but true statement is not a wrong record. The recall gate (≥ 0.70) uses strict (same only), because a vaguer statement doesn't recover the fact. Both variants are reported.
24. **Delete import vs messages shared with later imports**: SPEC §7 says to delete the messages the import "首次引入". Read literally, deleting import A would also remove messages that a later import B re-contained (and B's evidence with them). We instead reassign `first_import_id` to the earliest other import that contained the message (via `import_messages`) and delete only messages that no other import contained. We believe that is the intent: B still has those messages.
25. **Error taxonomy mechanics**: false positives are labelled in two steps. Deterministic labels first: invalid_evidence, sensitive_leak, and wrong_person for handles/relations/dates. Then an LLM judge sees the FP text, its evidence window (evidence ±2 messages), all persons' gold claims and all negatives, and outputs one label plus a `subLabel` for should_ignore. `transactionalAsClaimRatio` counts claims labelled should_ignore/transactional|coordination, so transactional claims the annotator did not list as negatives are counted too.
26. **Gold drift guard**: gold stores `parserVersion`, `messageCount`, `messagesSha256` (sender/time/body per idx, kind excluded so reclassifying a kind doesn't invalidate gold) and anchors. On mismatch eval refuses to score that zip.
27. **Offline prompt inputs**: `extractOffline` passes only what a real user would have typed at mapping time: sender persons labelled with their senderName, and the gold chat title, which the annotator must derive from sender names. Gold person labels and aliases, claims and negatives never reach the prompt.
28. **Token budget scope**: one counter per loop covers in-app extraction (dev server), eval and judge calls: `.dev/llm-budget.json` in dev/CLI. When deployed, the budget is the sum over `llm_calls` since `LLM_BUDGET_SINCE`, default the current UTC month. The orchestrator runs `pnpm llm:usage --reset --loop <id>` at loop start and copies `pnpm llm:usage --json` into STATUS.json `llmUsage`.
29. **Model choice** (revised round 3): `settings.extractModel` ∈ {`deepseek-flash`, `deepseek-v4-pro`} or null; `SettingsDTO.extractModel` is nullable and `getUserSettings` never fills a default, so null falls through to env `EXTRACT_MODEL` → `deepseek-flash`. `EXTRACT_MODEL` is validated as the same enum by `server/env.ts` (an unknown value is a config error, not silently ignored). `processNextJob` receives `env` in its opts and resolves per request; eval uses `--model` or the same env resolution. Settings UI shows "默认（deepseek-flash）" for null.
30. **Per-request deadline**: `jobs/next` has a 28 s deadline. The extract call gets ≤ 20 s. Dedup runs only if ≥ 4 s remain, else it is skipped (treated as no duplicates, counted in the eval report), so one window stays under SPEC/PLAN's 30 s budget. Eval's `extractOffline` applies the same per-attempt deadline by default (A7 #4).
31. **Health endpoint auth**: core's session middleware rejects unauthenticated requests centrally for everything except `/api/auth/*` and `GET /api/health`, so routes can't forget auth. SPEC §10 says "所有路由经 Better Auth session 中间件": health is the one deliberate exception, needed by the verify tool before login.
32. **Delete-all/export table lists** are explicit (ARCHITECTURE §11) and include `llm_calls` (raw_output is derived from the user's messages) and `extraction_jobs`. Better Auth tables are kept by delete-all.
33. **Hand-written failure cassettes** live in the testing module (`server/extract/__fixtures__/cassettes/`). `fixtures/cassettes/{synthetic,real}` hold only record-run output.
34. **Showcase pages for shared components** live at `/dev/<module>/<name>` (`app/(app)/dev/<module>/**`, module-owned; core's `dev/layout.tsx` returns 404 outside development).

### A6. Things SPEC leaves open (defaults for builders)
- **Group chat display names**: `display_group` handles are chat-scoped (`chatId` set); `display_private` also chat-scoped (the remark name applies to the account, but we can't know that). `mentioned` / `address_term` from `@显示名 称呼` are chat-scoped; `real_name` is global (`chatId` null). Recommendation for mapping uses exact normalized match of display name across any chat, reason text names the chat ("在『<chat>』中也叫这个名字").
- **Self display name drift**: user's own WeChat name may change between exports → `selfDisplayNames` is a list; mapping auto-selects self on any match.
- **Unseen message formats** (quote reply, recall, merged-forward, contact card, location, file, link, group system messages, Android): parser classifies recognizable prefixes when obvious (`[引用]`/"「…」\n- - -", "撤回了一条消息", `[文件]`, `[链接]`, `[位置]`, `[名片]`, `[聊天记录]`) into kinds `quote|recall|file|link|location|contact_card|forward|system`, otherwise `unknown` preserving raw text. Lines not matching the header rule stay in the previous body (never dropped). Android format: detection returns ParseError `no_messages` if no header matched, with UI message per §9.7. Synthetic ZIPs include invented-but-plausible variants, clearly labeled as guesses in the generator.
- **Pinyin grouping for non-Chinese labels**: first char Latin letter → that letter (uppercase); Chinese → pinyin-pro first letter (polyphonic surnames use surname mode: 曾→Z, 单→S, 解→X, 仇→Q, 区→O); digits, emoji, symbols, other scripts → `#` group, listed last. Sort within group by `label_sort` (full pinyin, then label).
- **Lunar leap months**: `important_dates.is_leap_month`. A leap-month lunar birthday recurs on the leap month only when that year has the same leap month; otherwise falls back to the regular month of the same number (common Chinese practice). Lunar day 30 in a 29-day month → day 29. Upcoming dates display "农历八月十五 · 9月25日"; solar Feb 29 in non-leap years → Feb 28.
- **"最近有新信息的人"**: persons with claims confirmed in the last 5 imports' review actions (by `review_log.created_at` of accept on items with those import ids), latest first, max 10.
- **"与我的关系"**: confirmed relation where one side is the self person; value shows `label` if present else Chinese of `type`.
- **High-confidence bulk confirm** (revised round 2): only **claims** carry confidence (SPEC §8.6). "确认所有可信度高的条目" = proposed claims of this import with `confidence >= settings.highConfidenceThreshold` and `sensitive = false`. Handles, relations, dates and events have no confidence and are never included; the user confirms them per item or with "本节全部确认". `ImportReviewResponse.highConfidence` lists the exact ids so the count shown equals what gets confirmed.
- **Timezone**: messages are naive local time; "today" and ISO display use `APP_TZ=Asia/Shanghai`.
- **exportedAt from ZIP filename**: interpreted as Asia/Shanghai local time → ISO with offset converted to Z. Missing/renamed file → null.
- **Chat kind with >2 senders** preselects group; exactly two preselects private but requires confirmation (SPEC).
- **Attachment upload limits**: images ≤ 20 MB each; videos unchecked by default and, if checked, ≤ 100 MB (R2 put from Worker).
- **Attachment upload lifecycle** (revised round 2; ARCHITECTURE §1.4): single owner = **import**. The overlay keeps the ZIP `File` in a module-level store keyed by importId; after mapping a module-level runner uploads selected media sequentially, independent of which page is mounted, so it continues on the import-result page (which only mounts import's `<AttachmentUploadStatus>`). After a reload the bytes are gone: server rows stay `selected=1, r2_key=null`, and the status line offers "重新选择这份文件继续" (sha256 must match). If ignored, the chat page shows "图片未导入". Holding the `File` (not unzipped bytes) keeps memory low.
- **Search**: SQL LIKE on `value_norm` / `statement_norm` (NFKC, lowercase, full-width → half-width), plus pinyin initials match on `label_sort` for Latin queries. No FTS5 in v1 (D1 supports FTS5 but not via drizzle-kit migrations cleanly; revisit if latency > 300 ms).
- **Evidence for manual items**: no evidence rows; UI shows "手动添加于 YYYY年M月D日" from `createdAt`.

### A7. Round-3 decisions
1. **Where the parsed export waits between step 1 and step 2: R2 staging.** Options were (a) R2 object, (b) chunked D1 staging table, (c) send messages again with the mapping request. Chosen: (a). `POST /api/imports` stores `StagedImportPayload` at `u/<ownerId>/imp/<importId>/parsed.json`; mapping reads it, runs LCS alignment against it, inserts messages, `import_messages`, then attachment rows (they need `message_id`), sets `extracting`, deletes the object. Why not (b): D1 caps a single value/row at about 2 MB (Cloudflare D1 limits page; not re-checked this round), so 50k messages need many chunk rows and a reassembly step, which is more code for no benefit. Why not (c): the ~10–15 MB body would be uploaded twice, and a failed or retried mapping would need the client to still hold the parsed export. R2 is already bound, and delete-all's `u/<ownerId>/` prefix delete covers the object. Owner: import.
2. **Abandoned imports (closed during step 2).** The overlay deletes the import when closed at step 2 (keepalive `DELETE`). As a safety net for a closed tab, `check` ignores `mapping` rows and `POST /api/imports` deletes a stale `mapping` row with the same sha before creating the new one, so `unique(owner_id, file_sha256)` never blocks re-importing. No resume flow: step 2 only asks for choices, which are quick to redo. `/imports/:id` for a `mapping` import shows "这次导入没有完成" + delete. Home's recent imports exclude `mapping`.
3. **Delete-import UI owner: import-result.** SPEC §9 places no delete-import control; PLAN §5's final flow needs one. It goes at the foot of `/imports/:id` as a quiet text button with a confirm dialog, then goes to `/`. Quiet and at the bottom so it does not compete with review actions (SPEC §9.3 tone). The chat page's import records only link to that page.
4. **Gold LOCK is append-only and committed for both sources.** The round-2 LOCK kept no history, so rewriting gold and LOCK together was undetectable, especially for gitignored real gold. Now `eval/gold/LOCK.json` holds `versions[]` per zip. Real zips are keyed by a hash of the ZIP (no names), so git history covers real gold too. freeze-gold only appends, and requires the DECISIONS `gold-change:` line before appending. Eval checks every later version has its line and that the working LOCK extends `HEAD`'s. `eval/gold/real/LOCK.json` no longer exists.
5. **Eval measures window time under the app's deadline.** `extractOffline` defaults to `deadlinePolicy: 'app'` (per attempt: deadline 28 s, extract ≤ 20 s with no transport retries, dedup only with ≥ 4 s left). `p95WindowMs` = nearest-rank p95 over all window attempts of extract + validation + dedup + persistence time; in replay it uses recorded call latency plus local compute. P4's gate is the integration test; the live/record eval p95 is its confirmation on real model latency. Consequence: eval now counts app-deadline timeouts as failed attempts, as the app does.
6. **Link tables carry `owner_id`.** `import_messages`, `claim_mentions`, `event_participants` and `evidence` have `owner_id` + `created_at`, a composite pk and no surrogate id. ## parser

Round 1 (2026-09-15). Module `lib/wechat-export`; public entry `@/lib/wechat-export` with the exact ARCHITECTURE §1.2 signatures (plus `isParseError`, `STICKER_CODES`, type re-exports).

- **P1 Splitting rule is the literal SPEC §6 rule.** A line whose first char is U+00B7 `·` AND whose next line matches `^\d{4}年\d{2}月\d{2}日 \d{2}:\d{2}$` starts a message; everything else (including `·` lines not followed by a timestamp, bare timestamp lines, consecutive `·` lines) stays in the previous body. Body = lines up to the next start with leading/trailing whitespace-only lines removed; inner blank lines and indentation are kept verbatim; no NFC/trim of the sender name (raw, so fingerprints stay stable). Other bullets (`・`, `•`) and other time formats (`2026-09-01 10:00:00`, `2026/09/01`) are NOT accepted: guessing Android formats would risk mis-splitting iOS bodies; such files get ParseError `no_messages` (A6). Unavoidable ambiguity: a body line `·x` directly followed by a line that is exactly a WeChat timestamp is split as a new message.
- **P2 Tolerances before splitting**: leading BOM stripped; CRLF and lone CR → LF; trailing spaces/tabs on the timestamp line ignored. Text before the first header is dropped with warning `preamble_text`. Empty sender (`·` alone) is kept as `''` with warning `empty_sender`. Empty body → kind `text`, body `''`.
- **P3 Warnings** (`{line, code}`, 1-based header line, 0 = file level): `preamble_text`, `empty_sender`, `attachment_no_name`, `attachment_missing`, `unknown_kind`, `time_out_of_order`, `duplicate_media_name`, `multiple_txt`, `decoded_gbk`. Never fatal.
- **P4 Kinds.** Tag = `[xxx]` at body start followed by space/end of line. Known tags from samples map per SPEC §6. Unseen-but-plausible tags are guesses: `[文件]`→file (meta.fileName, gets attachment linking), `[链接]`→link (title+url), `[位置]`→location, `[名片]`/`[个人名片]`→contact_card, `[聊天记录]`→forward, `[引用]`→quote, `[撤回]`→recall, `[系统消息]`→system, `[微信转账]`→transfer, `[表情]`→animated_sticker, `[语音通话]`→video_call with `meta.label` "语音通话…" (no voice_call kind in the contract; it's a call, not a voice message). Untagged heuristics (single line only): recall = `"名字" 撤回了一条消息` / `你撤回了一条消息`; system = quoted-name forms of 邀请…加入了群聊 / 修改群名为 / 移出了群聊 / 拍了拍 / 通过扫描二维码加入群聊 / 你已添加了…; quote = a `「名字：原文」` block on its own line(s) either trailing the reply or followed by a `- - -` separator (WeChat's copy format). Plain prose like 我拍了拍他 stays text. Body is always kept raw; meta is a hint.
- **P5 sticker_code vs unknown.** Whole body made only of `[xxx]` tokens: ≥ 2 tokens → sticker_code; a single token → sticker_code iff it is in the built-in WeChat emoji list (`STICKER_CODES`, ~250 CN/EN names), otherwise `unknown` with `meta.label`. `[emoji] text` or text containing codes → text. An unrecognised `[xxx] rest` prefix (xxx not an emoji code) → unknown; `[xxx]rest` without a space → text.
- **P6 Attachments.** `attachmentName` = the matching `media[].name` (exact, then NFC/case-insensitive); empty filename → null + `attachment_no_name`; filename present but not in the ZIP → null + `attachment_missing` (the name stays in `meta.fileName`). Import creates the attachment row with `file_name` null / `selected` 0 for both (ARCHITECTURE §1.4). `media` = every non-txt entry (skips directories, `__MACOSX/`, `._*`, `.DS_Store`); kind by extension (images jpg/jpeg/png/gif/webp/heic/heif/bmp, videos mp4/mov/m4v/3gp/webm, else file); `referenced` = some message links it. Media bytes are not inflated during parsing (fflate filter; sizes from the central directory), so parsing cost doesn't grow with video size.
- **P7 ZIP entry names.** WeChat iOS writes UTF-8 names without the ZIP UTF-8 flag (verified on all 3 real samples); fflate then decodes them as latin1. Names are re-decoded strict UTF-8 → strict GBK → left as is. txt choice: `聊天记录.txt` (shallowest) else the largest `.txt`. Text decoding: UTF-16 by BOM, strict UTF-8, strict GBK (warning), else ParseError `bad_encoding`.
- **P8 Hashes.** `fingerprint` = FNV-1a 64 over the UTF-8 bytes of the literal contract template `${senderName}${sentAt}${kind}${body}` (no separators, as written), computed with 16-bit limbs (no BigInt); tested against a BigInt reference. `sha256Hex` uses `crypto.subtle` and falls back to a built-in pure-JS SHA-256 when `subtle` is missing: browsers hide it on insecure origins, e.g. the dev server opened by LAN IP over http. `parseExportText` has no ZIP bytes, so `sha256` is `''`, and it throws `ParseError('no_messages')` like the ZIP path.
- **P9 exportedAt**: `YYYYMMDD_HHMMSS` anywhere in the file basename, Asia/Shanghai (fixed UTC+8) → ISO Z; invalid dates → null. **Senders** in `ParsedExport` are in first-appearance order; `summarize()` sorts by count desc (ties by first appearance). Preview images/videos = media entries in the ZIP (what can be uploaded), not message counts.
- **P10 Mentions** (`extractMentions`): the name ends at U+2005 (what WeChat inserts; seen in samples), with a plain space as fallback. `addressTerm` = the next token of ≤ 4 chars when a space, punctuation or end of body follows it. This is a candidate only (`@x 你好` yields 你好); extract/LLM decides. Emails are skipped.
- **P11 PARSER_VERSION** = `wechat-export@1` (`@2` since P14).
- **P12 Perf.** Node (vitest `perf.test.ts`, 5001 messages, 16 MB ZIP with 40 images + 8 MB video): median ≈ 30 ms, assert ≤ 1.5 s (P1b). System Chrome 153 (Playwright, `lib/wechat-export/scripts/browser-perf.ts`, same ZIP, https route so WebCrypto is used): first run 64 ms, median of 3 = 50 ms, budget 3 s (P1). vitest 5 no longer exports `bench`, so P1b is a timed test, not a `vitest bench` file.
- **P13 Real-sample check** (`npx tsx lib/wechat-export/scripts/check-real.ts`, counts only): messages 33 / 37 / 66, equal to an independent `awk` count of `·` lines followed by a timestamp line, and to `grep -c` of timestamp lines. All kinds seen in the samples classify with zero `unknown`; every non-empty image/video name links to a ZIP entry. The 2 empty image names in one sample give `attachment_no_name`.
- **P14 Fingerprints ignore generated media file names (overall critic r1, 2026-09-16; PARSER_VERSION `wechat-export@2`).** WeChat names exported media `微信图片_<YYYYMMDDHHMM>_<n>.<ext>` / `微信视频_…` from the **export** time, and `n` counts through the export. - **P15 Image mime from the leading bytes (overall critic r3 #1, 2026-09-16; PARSER_VERSION unchanged).** WeChat exports HEIC photos as `微信图片_….jpg`, so the extension alone gave `media[].mime` `image/jpeg`. - **L5 Transport semantics**:
  - The adapter retries `network`, `http_5xx`, `rate_limited` and `empty_content`, backing off 1 s then 3 s. For 429 it honours `retry-after`, capped at 30 s.
  - A retry is skipped, and the last error returned, if its sleep would leave less than 1 s before `deadlineAt`.

  - One surrounding ```json fence is tolerated before JSON.parse.
- **L6 `LlmError.retryable`** means "the identical request may succeed". It is true for `timeout`, `network`, `http_5xx`, `rate_limited`, `empty_content` and `invalid_json`. It is false for `http_4xx`, `truncated` (the same max_tokens truncates again), `cassette_miss`, `budget_exceeded` and `deadline`. Extract still owns semantic retries (§5).
- **L7 Logging**: every attempt produces one record. That includes outcomes that never reach the provider (`budget_exceeded`, `deadline`, missing key, `cassette_miss`), which get null tokens and latency 0 so refusals can be audited. - **L8 Budget**:

  - The `fileBudget` limit comes from the file (set on reset), else `LLM_BUDGET_TOKENS`, else 3M. A missing file is created on the first add with loopId `unset`.

- **L9 Replay**:
  - No transport retries or backoff: the same cassette always gives the same outcome.

## review

Round 1 (2026-09-15). Public entries `@/server/review` and `@/components/evidence`; contract shapes unchanged.

- **R1 Supersede on confirm.** `accept` (single, bulk, or `edit` of a proposed claim) of a claim with `supersedesClaimId` marks that older claim `superseded` / `status_reason 'superseded'` / `superseded_by_claim_id = new`, if it is confirmed or proposed. Rejecting a confirmed claim that had superseded another restores the older one to confirmed. Superseded rows are read-only: accept/reject/edit → 409 `conflict` (bulk reports `code: 'conflict'`).
- **R2 Edit.** Proposed/rejected claim: edited in place and confirmed (reviewLog `before`). Confirmed claim: new confirmed row (copies evidence, source kind, import id, confidence; `supersedes_claim_id = old`), old row `superseded/edited` (A5 #9). Handles/relations/events/dates are edited in place and confirmed, with no history. Edit with no effective fields → 400. Mentions (`claim_mentions`) are recomputed from other active persons' labels (≥ 2 chars) found in the statement, for edits, replacements and manual claims.
- **R3 Supersede ("已过时").** Claims only (other types → 400); only confirmed (→ 409). Sets `validTo` = today in APP_TZ, reason `outdated`; `replacement` creates a manual confirmed claim, same category, `supersedes_claim_id = old`, and old `superseded_by_claim_id` points to it.
- **R4 Delete item.** Hard delete of item + evidence + claim_mentions/event_participants. A claim it had superseded (reason `superseded`) becomes confirmed again; edited/outdated originals only lose the pointer. Deleting a handle nulls `messages.sender_handle_id` (raw `sender_name` stays).
- **R5 reviewLog for actions without an item target type.** `review_log.target_type` is TargetType (no `person`), so merge writes one `merge` row per moved handle/claim/date/event/relation, split writes one `split` row for the handle plus one per candidate item, and manual adds write `edit` with `before: null, after: { created: 'manual', … }`. `POST /api/people` writes no log. Not worth a contract change.
- **R6 Import status.** After any review action the affected imports move `reviewing → done` when none of their items is `proposed`, and `done → reviewing` when some are again (split candidates). Imports in other statuses are untouched.
- **R7 Import review grouping.** Items = rows with `import_id = :id` and `source_kind 'ai'`, all statuses (handled items stay in place), except originals of a person-page edit (`status_reason 'edited'`). "变化" = claims whose `supersedesClaimId` points to a claim that is not their own edit original. Relations/events touch several persons: section = a non-self endpoint created by this import, else one that already has a section, else the first non-self. `newCount` counts all of the section's items in this import (not only proposed) so sections do not reorder while the user reviews. Sort within groups: claims by category order work→other, others by id; handles before relations.
- **R8 Evidence segments.** Evidence messages ±context in the same chat. Windows in one chat merge into a single `EvidenceItemDTO` only when they share a message or the second starts at the chat message right after the first window ends (round 2, see R14) (several `isEvidence` messages; `messageId` = first evidence message), so a message never repeats. Segments are ordered by the first evidence message's time. Contract allows it (per-message `isEvidence`).
- **R9 Merge details.** `from` self → 409; either side merged → 409; same id → 400; merging into self is allowed. Relations: endpoints remapped; self-loops deleted with their evidence; exact duplicates `(from, to, type)` fold into the existing relation (evidence union, confirmed wins). `from.pinned` carries over to `into`; persons merged into `from` are re-pointed to `into`.
- **R10 Split details.** Items of the original person with ≥ 1 evidence row whose messages were all sent by the split handle are candidates; confirmed ones go back to `proposed` (proposed ones stay and are listed); superseded/rejected are skipped. `last_message_at` is recomputed for both persons. The new person has no `import_id`.
- **R11 Manual relation direction.** `POST /api/people/:id/relations { toPersonId, type, label }` stores `from = :id`, `to = toPersonId` in the §2.5 reading (`from` 是 `to` 的 `type`). Person UI must phrase its form accordingly. Manual events always include `:id` as a participant.
- **R12 Evidence UI.** The block sits directly under the row (for `as="p"` it is rendered as the paragraph's next sibling, because a `<div>` inside `<p>` is invalid HTML). Time: the first message of a segment and any message on a new day use `formatMsgTime 'full'`, the rest `'short'`, so repeated dates don't crowd the line (deviation from "full" on every line in §2.8). Chips: voice "语音 N 秒", transfer "转账" + state text, red packet "红包" + greeting, video call "视频通话" + duration, and also image/video/动画表情/小程序/视频号/文件/链接/位置/名片/聊天记录, followed by their visible title text. An AI item with no remaining evidence shows "原话已经不在了". The error message is "原话没有加载出来 · 重试", shown while the row stays intact. A refetch after an error shows the skeleton.
- **R13 Showcase.** `/dev/review/evidence` uses synthetic fixtures in a local QueryClient (staleTime ∞, retryOnMount off): data seeded with `setQueryData`, loading = a never-settling fetch, error = a query already in the error state, so no network calls are involved. `?claim=&claim2=` adds rows backed by the real API for seed claims; the scenario uses them for loading (delayed route), 500 error, and retry.
- **R14 Evidence adjacency (round 2).** Chat `seq` has gaps (steps of 1024), so adjacency is not a seq difference or a position in the fetched list. Each window fetches `ctx + 1` messages after the evidence message; the extra one (not shown) is the window's chat successor. Two windows merge iff they overlap by seq or the next window's first message is that successor. Far-apart evidence therefore gets its own segment and its own "在聊天中查看" link.
- **R15 D1 parameter cap (round 2).** Multi-row inserts are chunked by column count (`rowsPerInsert(cols) = ⌊96/cols⌋`: link tables 24 rows, evidence 19, review_log 12). Batches hold ≤ 100 statements (ARCHITECTURE §4.2).
- **R16 Bulk plans against evolving in-memory state (round 2).** Planning an item updates the loaded rows (status, supersede pointers, restores), and a claim appears as one shared object across the item list and its related claims. A claim that an earlier item in the same request supersedes is reported `conflict` and stays `superseded`. Listing the old claim first confirms it, then the replacement supersedes it; statements run in item order.
- **R17 Undo instead of transactions (round 2).** Rows that must exist before the batch (the new claim for an edit of a confirmed claim or for a replacement, the new person for a split, manual items) are removed by an idempotent undo if the batch fails; the undo also restores the original claim or the handle's person. In a merge, the person rows (`mergedIntoId`) come last, after the review_log rows, so if a merge longer than one batch is cut off it can be run again.
- **R18 Import review counts only shown items (round 2).** A handle without a person and an event without participants have no section, so `allHandled`/`empty` ignore them.
- **R19 Evidence UI details (round 2).** On narrow screens (< 640px) the mark has an invisible hit area of about 27×27 px (`[data-evidence-hit]`); the glyph itself is unchanged. Inside the bordered block, BlockError drops its own left rule. For element shots in the showcase scenario, the top bar is switched to non-sticky just for the shot.

Wave 5 (2026-09-16), 交互层. Public entries unchanged. Core requests review#1 (the `loop` review contracts) and review#2 (`owned()` over the interaction tables) landed during the wave; the local workarounds are gone and nothing in review shadows a contract type any more.

- **R20 Loops are reviewable, segments are not.** `applyReview(db, ownerId, {type:'loop', id}, …)` supports accept / reject / edit / delete and writes `review_log` like every other type; `supersede` stays claims-only. `segment` fails fast: `applyReview` asserts reviewability before it loads the row (400 `validation_failed`), and `bulkReview` reports each segment as `{code:'validation_failed'}` instead of counting it as updated. The reason is SPEC §9.9: a 段落摘要 says what was said that day, it is not an assertion about a person, so there is nothing to confirm, and one import produces dozens of them. Editing or hiding a segment is `PATCH /api/segments/:id` (interaction). `GET /api/evidence/segment/:id` still works — reading the original messages is not reviewing.
- **R21 Two table maps.** `TABLES` has an entry per `TargetType` so indexing it typechecks and so evidence can load a segment row; `REVIEWABLE` is `TABLES` minus `segment` and is what `syncImportStatus` sweeps. `conversation_segments` has neither `status` nor a review meaning, and iterating `TABLES` would have queried a column that does not exist.
- **R22 Loop derivation lives in review too.** `state` / `expired` / `daysOpen` are computed by `server/review/loops.ts`, not imported from `@/server/interaction`: both modules are built in the same wave, and review must not depend on a sibling that is still mid-flight. Both read SPEC §7 交互层 and the same two constants (`LOOP_EXPIRY_DAYS_WITH_DUE = 14`, `LOOP_EXPIRY_DAYS_NO_DUE = 90`). The dependency points one way only: review never imports `@/server/interaction`, and `dueDay` here is the **canonical** reading of a PartialDate due date for the whole app — interaction imports it from `server/review/loops.ts` instead of re-deriving it, so the two sides cannot drift by luck. Rules: closed iff `closedMessageId` or `closedReason` is set (a loop closed by hand has only the reason), `state = closedReason ?? 'done'` when closed; `daysOpen` runs to the close day, else to today, never negative; a closed loop is never `expired`. A PartialDate `dueAt` means the **last** day it can stand for (`2026-09` → `2026-09-30`), so a plan is not called expired before its month is out.
- **R23 Loop edit.** Patch `{text?, dueAt?, kind?, direction?}`, edited in place and confirmed, with the old values in `review_log.before` — the same shape as handles/relations/dates/events (R2), no history row. `dueAt: null` clears the due date and counts as a real edit; an empty patch is 400. `text` is trimmed and `text_norm` recomputed. `supersede` on a loop is 400: only a claim can be 已过时.
- **R24 未结事项 group in the import review.** `sections[].loops` holds this import's AI loops, oldest `openedAt` first. They count towards `newCount`, `allHandled` and `empty`, but never towards `highConfidence` — a loop has no confidence score, exactly like handles/relations/dates/events (A6). An older loop that this import *closed* is not in the group: it keeps the `import_id` of the import that opened it, so it shows up in 「这次聊了什么」 with nothing to confirm (SPEC §9.9).
- **R25 Merge folds `segment_participants`, sums on collision.** Loops move by `person_id` like claims. `segment_participants` has pk `(segment_id, person_id)`, so when both persons spoke in the same segment the insert is an `onConflictDoUpdate` adding `excluded.message_count` — the two rows counted different messages of one conversation. `moved` gains `loop` (loops moved) and `segment` (participant rows folded; the segment itself does not move, only who spoke in it). Chunk size is `rowsPerInsert(5)`, not `LINK_ROWS`, because the row has five columns.
- **R26 Reopen-on-delete has to run before the messages do (ARCHITECTURE §11 step 7, milestone M7).** `loops.closed_message_id` is FK `on delete set null`, so once M is gone there is nothing left to tell a loop closed by a deleted message from one the user closed by hand (`closedMessageId` null, `closedReason` set). The `update loops set closed_message_id = null, closed_at = null, closed_reason = null where closed_message_id in (M)` therefore rides in the item batch, which commits **before** the batch that deletes the messages. A delete cut off between the two batches has already reopened; re-running it is a no-op. There is no post-hoc repair, and there cannot be one.
- **R27 Segments are decided by their span, loops by their evidence.** Loops go through step 2/3 like any derived item. Segments go through step 2 (every evidence message in M → deleted, with participants and evidence) but are **excluded from the step-3 AI sweep**: a segment is tied to `[start_seq, end_seq]`, not to the assertions inside it, so an AI segment with no evidence rows at all must not be swept away while the messages it summarises are still there. Instead, after M is deleted, one pass over the import's chat deletes segments whose span is now empty and recomputes `message_count` / `started_at` / `ended_at` of the rest from the messages still inside the span (`coalesce` guards the two not-null columns). Both statements are idempotent recomputations, so an interrupted delete heals on re-run. `deletedItems.segment` counts both routes.
- **R28 `segment_participants` is recomputed, not just pruned.** ARCHITECTURE §11 asks for the rows of persons with no remaining message in the segment to be dropped; the pass recomputes `message_count` from the messages still in the span first and then deletes the rows that came out 0, which is the same set and also stops a stale count from being carried into a later merge (R25). Scoped to the deleted import's chat, since every message in M belongs to it. The persons-created-by-this-import orphan sweep gained a `not exists (select 1 from loops …)` guard, so a person the import created but who still has an open loop is not deleted out from under it.

## extract

Round 1 (2026-09-15). Public entry `@/server/extract` has the ARCHITECTURE §6 signatures plus additive exports (`d1Store`, `memoryStore`, `getProgress`, `applySensitiveGuard`, `detectSensitive`, `renderDedupPrompt`, `getPrompt`, `listPromptVersions`, `DEDUP_PROMPT_VERSION`).

- **X1 Prompts are bundled, not read at runtime.** Workers have no fs. `server/extract/scripts/gen-prompts.ts` compiles every `prompts/*.md` (front-matter `version`, sections `system` / `user_template` / `example_json`) into `server/extract/prompts.generated.ts`. `prompts.test.ts` fails when that file is stale or a version differs from its file name. Old versions stay in the registry, so `pnpm eval --prompt/--compare extract.vN` keeps working.
- **X2 Windowing.** A gap of more than 3 h starts a new session (exactly 3 h does not). Inside a session, new messages are clustered when at most 40 existing messages separate them. Each cluster gets up to 20 existing messages on each side (never across a session boundary). The span is then cut into windows of at most 150 messages, overlapping by 20. Windows without a new message are not created. The last window can be short (151 messages → 150 + 21); it is not rebalanced.
- **X3 Context messages (SPEC §8.4).** In-app, a message is context when its `first_import_id` is not the job's import (additive `WindowMessage.context`). The prompt marks those lines 【上下文】. Validation drops items whose evidence is only context messages (`context_only`); context evidence next to a new message is kept. Offline runs have no context (focus = whole export).
- **X4 Strict validation per item, not per window.** The top level stays strict: a non-object, an unknown key or a non-array value is `validation_failed` and retried. Each array item is parsed with its strict zod element schema, and an invalid item is dropped (`invalid_item`). At temperature 0 a retry would reproduce the same bad item, so failing the whole window would lose every good item after 3 identical attempts. Before the strict parse: null optional fields are removed, strings trimmed, evidence `"#12"`/`"12"` → 12, bare ids/strings in person positions → PersonRef. Additive drop reasons: `invalid_item`, `context_only`, `self_loop`.
- **X5 Item rules.**
  - An evidence seq outside 1..n drops the item (SPEC §8.6).
  - An unknown `supersedesClaimId` is stripped; the claim is kept.
  - A `newPersons` entry whose label equals a known person's label or handle becomes that person.
  - A handle equal to a name the person already has is dropped. Sender display names come from mapping, and GOLD_FORMAT.md says they are not handles.
  - Exact duplicates within a window merge their evidence. Relation types are lowercased. Events keep only known participants.
  - `newPersons[].evidence` is not gated (person rows have no evidence). A tempId that no surviving item references creates no person.
- **X6 Sensitive guard** (deterministic, after validation).
  - Patterns are at least as strict as the harness detector: phone incl. landline, ID and bank card numbers after joining digit groups; digits next to 号/栋/幢/单元/室/弄 (not after 月); 路/街/巷 + digits + 号.

- **X7 tempId resolution across windows.** A new person is reused when this import already created a person with the same normalized label. It is also reused when that person's label contains, or is contained in, the new label (≥ 2 chars) and it already has evidence on one of the same messages. Otherwise it is created (`persons.import_id` = this import, `label_sort` via lib/pinyin).

Candidates are this import's proposed/confirmed claims plus confirmed claims overall for that person, last 80. Entries naming an index or id outside their group are ignored.   - Each item and its evidence / mentions / participants are in the same batch, which D1 runs as one transaction. A new claim's id is read inside the batch as `max(id)` over the owner's claims; relations, dates, events and handles are found by natural key.

## import

- **I1 Alignment (SPEC §8.4).** `alignMessages` is an exact LCS over fingerprint sequences: drop elements whose fingerprint does not occur in the other sequence (a disjoint re-import stays O(n)), trim the common prefix/suffix, then Myers O((N+M)·D) on the rest. Past D = 1000 it falls back to a greedy in-order match, which is not optimal; this is recorded because it only matters for pathological reorderings. Same-minute duplicates (two "嗯") match pairwise and are never collapsed. Unmatched messages go after the last stored message sent at or before them, between the matched anchors. This uses an optional `sentAt` on `existing`, additive to the §1.4 signature (core request import#3). New seqs are spaced evenly in their gap. When a gap is too small, the chat is **renumbered** (round 2, replaces the ×1024 rescale): stored message k → (k+1)·unit, unit = smallest power of two ≥ (largest bounded gap + 1)·1024; stored seqs above 2^44 (legacy rescales) also trigger it. Old values are never multiplied, so repeated prepends stay bounded (max ≈ stored count × unit); every seq is asserted ≤ 2^52. See I15 for the D1 side. The renumber runs **before** the inserts, so the new seqs are computed against the renumbered values.
- **I2 Mapping claim.** `POST /mapping` claims the import with a conditional `mapping → parsed` update, so a double submit cannot insert twice. On any failure it deletes the rows it inserted (messages with `first_import_id`, links, attachments, jobs, handles/persons/chat it created) and returns the status to `mapping`. The staged payload is kept, so step 2 can be retried. `check` and `POST /api/imports` treat `parsed` like `mapping`: stale, never a duplicate.
- **I3 Seam with extract.** `createJobsForImport` reads `imports.chat_id` (409 when null), so mapping links the chat just before creating jobs. `extracting` is still set in the final batch. The integration test uses extract's real function, not a mock; the mock had hidden exactly this.
- **I4 Delete-import extension (§11).** Mapping creates display handles with `source_kind='manual'` and `import_id` = the import. They carry no evidence, and `ai` would make §11 step 3 delete them while other imports still use them. Deleting an import also deletes those handles when no remaining message uses them and they have no evidence outside M. Without this, a person created by the import could never be removed while the chat survives. Round 2 closes the A→B gap: before the import row is deleted (FK `set null`), manual display handles and non-self persons with `import_id` = this import are handed to the earliest other import that still uses them (handles: an import linking a message they sent; persons: via their handles' messages, then handles/claims/dates of another import), so deleting that import later removes them as "created by this import". Chosen over a broad "any empty person" sweep so a person the user made by hand is never deleted by an import delete.
- **I5 Sender → person.** Handle kind follows the chosen chat's kind. The value is the raw display name, scoped to the chat, `confirmed`. An existing handle that points at a different person is re-pointed to the user's pick. The first "我" pick creates the self person, labelled with that display name, when none exists. A pick of a merged person resolves to its `merged_into_id`.
- **I6 Chat recommendation.** My own display names (settings `selfDisplayNames`, or any handle of the self person) never count, because I am in every chat. score = matched non-self senders / non-self senders. Step 2 preselects an existing chat only at score 1 or when `open({ chatId })` names one; otherwise it preselects "新建聊天". The kind is preselected as 私聊 for 2 senders and 群聊 for more, with the private title defaulting to the other sender's name. matchReason: `『名字』在这个聊天里出现过` / `『名字』等 N 人…` / `所有发送者都在这个聊天里出现过`.
- **I7 Sender suggestions.** Candidates rank in this order:
  - a display handle in a chat: 在『聊天』中也叫这个名字
  - another handle kind: 也被称为这个名字
  - a label equal to the name: 人物名就是这个名字
  `suggested` is `{self}` when the name is in `selfDisplayNames` or the top candidate is the self person; otherwise it is the top candidate. ## interaction layer (orchestrator, 2026-09-16)

设计讨论的结论，先写在这里，再落到 SPEC §7 交互层 / §8.8 / §9.3–§9.9 和 ARCHITECTURE §1.17 / §4.1 / §6 / §7 / §11。

- **I1 为什么加这一层。** 原来的记忆模型只有语义记忆（persons → claims/relations/dates），回答"这个人是谁"。它回答不了"我们上次聊了什么、还有什么没了结、我们多久来往一次"。更糟的是 `extract.v8` 第 76 行明确要求丢掉即时协调，而丢掉的东西没有第二个去处。所以这一轮不是加规则，是加去处：长期事实 → claim，这次来往 → segment，悬而未决 → loop，三者都不是才不记。

- **I2 会话不建表。** `windowing.ts` 早就按 3 小时间隔切会话，只是切完就扔。但会话边界会漂移：这次导入停在 21:00，下次补上 21:30 的消息，两段就并成一段。所以摘要挂在**窗口区间**（`chatId + startSeq..endSeq`，唯一约束）上，会话是 `groupSegments()` 读时聚合。边界变了只是重新分组，已有摘要不作废。3 小时这个常数收敛到 `contracts/common.ts` 的 `SESSION_GAP_HOURS`，分窗和聚合共用一个定义。

- **I3 loop 不存状态机。** open/done/dropped 由 `openedMessageId` / `closedMessageId` 两个事件推出，`expired` 读时算。代价是查询多一次 join，换来的是乱序导入（先导 9 月再导 3 月）、重复导入、删除导入三件事自动正确 —— 关闭只认消息时间，不认导入时间。删除导入时 `closed_message_id` 落在被删消息里的 loop **重新变回未结**（ARCHITECTURE §11 step 7），因为关闭它的那句话已经不在了。这是 SPEC M7 的验收点。

- **I4 摘要不走确认，未结事项走确认。** "AI 只提议"（SPEC §3）针对的是**对人的断言** —— 写进档案、会被当成事实的东西。段落摘要描述的是"那天聊了什么"，错了污染不了人物档案；而一次导入会产出几十段摘要，逐条确认会把导入结果页压垮。所以摘要默认可见、可改写、可隐藏，不进待确认流，不计入 `allHandled`/progress。loop 相反：它会出现在首页和人物页、会影响用户接下来做什么，所以保留 proposed/confirmed，但复用 SPEC §9.5 的"未确认条目就地显示、颜色降一档"，不集中不计数。用户点"已完成/不用管"本身就是确认动作。

- **I5 不破 §9.3。** 交互层最容易滑向"提醒系统"。明确写死：没有全局未结事项列表、没有条数、没有按久未联系排序的名单、没有警示色。节奏是描述不是催促，只出现在人物页上。首页只多一样：带明确日期的约定并入已有的"即将到来"（那本来就是一份按日期排的清单）。会话少于 `MIN_RHYTHM_CONVERSATIONS`（5）时不写平均间隔 —— 三次聊天算不出节奏。群聊不算"谁先开口"和回复间隔，因为群里回复归属不明确、导出也没有秒（SPEC §6）。

- **I6 不加第二次模型调用。** segment / loops / closes 和 claims 在同一次窗口调用里产出，输出 token 多 20–30%，输入侧每人多 100–200 token（上次来往 + 未结事项列表）。loop 判重搭现有的每窗口一次 dedup 调用。§6 的 28 秒 per-request deadline 里没有第二次调用的余量。

- **I7 约定不造第三种实体。** "下个月去成都"是 `kind='plan'` 且带 `dueAt` 的 loop，首页直接读它，不再生成 event。`events` 继续只表示**已经发生的**人生节点。

- **I8 评测是扩展不是修改。** `goldVersion: 2` 的 `loops` / `conversations` 是可选字段，v1 金标准文件保持有效且**分数不变**（有回归测试守着）。PLAN 禁止的是为了提高分数改金标准，新增类别不在此列。loop 精确率入闸（≥ 0.80），召回率本轮只报不闸 —— 新能力没有基线。v9 的分流规则会让一部分原来被记成 claim 的文本改去 segment/loop，claims 的指标会动，报告必须把这个变化显式列出来，不许埋掉。

- **I9 LLM 预算（orchestrator，2026-09-16）。** loop 1 收尾时用掉 2,880,757 / 3,000,000 token，只剩 ~119K。`extract.v9` 落地后 `PROMPT_VERSION` 变成 v9，而现有磁带录的是 v5–v8，所以 `pnpm eval` 回放跑不了 v9，必须实录一次（extract 估计 ~180K token）。剩余额度不够，按 PLAN「模型调用成本」的规则不能超支。交互层这一轮是 loop 2，所以把计数器 `--reset --loop loop2-interaction` 归零重新计。归零的是计数器，不是已经花掉的钱：loop 1 的实际消耗记在 STATUS.json 的 `llmUsage.note` 里，没有抹掉。在 v9 实录完成之前，任何声称达到 §7.4 闸门的说法都是无效的 —— 现在根本没有 v9 的测量值。

## interaction

Wave 5 builder decisions for `server/interaction/**`, `components/interaction/**`. The orchestrator's I1–I8 above are the why; these are the how, and only the choices the spec left open.

- **X1 `groupSegments` is order-free and returns oldest first.** It buckets by `chatId`, sorts each bucket by `startedAt` then `startSeq`, and joins a segment to the running group when `minutesBetween(group.endedAt, segment.startedAt) <= SESSION_GAP_HOURS * 60`. Exactly 3 h apart is one conversation, 3 h 1 min is two. The running `endedAt` is the max, so an overlapping re-extraction of a wider window does not shorten the group. Because the rule reads the sorted list rather than the input, a reverse-order import produces an identical answer — asserted in `pure.test.ts`, together with the drift case (two segments 3.5 h apart are two conversations until a later import lands between them, then one).
- **X2 Hidden segments still shape the conversation.** A hidden summary is left out of the person page's timeline, but it keeps its place in the grouping and in `messageCount` — hiding a sentence you wrote about a day does not change what happened that day. A conversation whose every segment is hidden disappears from the timeline. `GET /api/imports/:id/interaction` includes hidden segments (flagged) so "隐藏" can be undone where it was done.
- **X3 `expired` starts the day after the threshold.** More than 14 days past `dueAt` (the last day a partial `dueAt` could still have happened: `2026-08` → `2026-08-31`), or more than 90 days past `openedAt` — "过期 14 天后" reads as *after* those days, so day 14 is not yet expired. This matches `deriveLoop` in `server/review/loops.ts` exactly, because the import result page and the person page must not disagree about the same row (core-request interaction#5 asks for the two copies to be collapsed; until then `pure.test.ts` pins the boundary on both sides). `daysOpen` runs from `openedAt` to `closedAt` for a closed item and to today otherwise, never negative. Closed items are never expired. `已过去 N 天` counts from the due date when there is one, otherwise from the opening.
- **X4 Rhythm suppresses more than the average under the minimum.** SPEC §9.5 forbids the average gap below 5 conversations; the sentence also drops "谁先开口" there, because "只写最近一次和总次数" is the whole instruction. The initiator clause additionally needs at least 3 attributable conversations and a 60 % majority, otherwise it says "你们先开口的次数差不多". The other side is named "对方", not a pronoun and not the person's label — the section is mounted with only a `personId`, and "TA" is banned on the self page.
- **X5 "Who spoke first" is the sender of the message at the first segment's `startSeq`.** Private conversations only. If that sender maps to neither the self person nor this person (a merged or unlinked handle), the conversation contributes nothing rather than guessing.
- **X6 Timeline paging slices conversations, not segments.** `?timeline=5` returns the 5 newest conversations whole; `hasMore` counts conversations, and only the segments actually rendered are decorated with participants and `firstMessageId`. `更早` refetches with `timeline=all` and keeps the previous data on screen (`keepPreviousData`).
- **X7 The rhythm sentence has no sub-heading.** It reads as the section's lead paragraph directly under 来往; 未结事项 and 来往时间线 carry small serif labels. A label over a single sentence would turn a description into a stat card, which SPEC §9.5 rules out explicitly.
- **X8 Segments carry a link, loops carry an evidence mark.** SPEC §9.5 gives the timeline "在聊天中查看" per segment and the unfinished items "证据标记"; the section follows that literally rather than putting a footnote on every summary, which would number dozens of marks on one page. Loop marks are numbered from `markStart` (default 1) — see core-request interaction#3.
- **X9 `closeLoop` sets `closedAt = now` and leaves `closedMessageId` null**, and lifts `proposed` to `confirmed` (SPEC §7: closing is confirming). `reopenLoop` clears all three close columns but does **not** un-confirm: the user's judgement about whether the item is real survives reopening it.
- **X10 The 即将到来 约定 rows take full and month-level due dates.** `2026-10` is placed on 2026-10-31, the last day it could still happen; a bare `2026` is too vague for a dated list and is left out. A closed or rejected plan leaves the list immediately, because it is queried by the absence of a close event rather than by a stored state.
- **X11 `这次聊了什么` shows its two actions without hovering.** The person page hides 改写/删除 until hover because it is a reading page; the import result page is where the user is reviewing, so 改写 and 隐藏 are visible (quiet, `text-ink-3`). There are still no confirm buttons anywhere in that block, it contributes nothing to progress, and it is outside the bulk-confirm range (SPEC §9.9).
- **X12 The infobox summary is one line.** `最后一次聊天` shows "9月13日 · 3 天前" and, under it, the newest conversation's first summary truncated to one line (SPEC §9.5 "下面一行小字"); clicking it expands every segment of that conversation with its own chat link. The summary is only shown when the newest conversation actually reaches the last-contact day, so the infobox never attributes an old summary to a recent message.
- **X13 No copies left.** Everything interaction had duplicated at the start of the round was collapsed during it: owner scoping (core widened `OwnedTable` / `OwnedLinkTable`, so every query calls `owned()` from `@/server/db`), query matching (`server/interaction/text.ts` re-exports search's helpers), the loop-state rule (`server/interaction/loop-state.ts` re-exports `@/lib/loop-state`, shared with review) and the due-day reading on the client (`components/interaction/format.ts` imports `dueDay` from the same place). Core-requests interaction#1–#5 are all resolved; the tests in `server/interaction/__tests__/pure.test.ts` stay as the shared rule's test suite.
- **X14 A loop is worded at render time, not in the database.** `loops.text` is a bare fragment ("把清单发过去"); `loopSentence` from `@/lib/loop-text` puts the subject and verb around it using `direction` and `kind`, which are never printed. `direction` says whose move is next, so a question the other person asked and the user has not answered is `question` + `mine` and reads "林知夏问你国庆有没有空，你没回". Sharing the wording with the import result page is the point: for one round the same item read two different ways on two pages.
- **X15 A conversation with every summary hidden leaves the timeline but stays in the rhythm.** Hiding a summary is a statement about the summary, not about the day, so `conversationCount` still counts it; there is simply no row left to render. On the seed account this is visible: 19 conversations counted, 18 listed. The scenario asserts the difference rather than either number alone, so the rule cannot drift silently.

- **I10 `direction` 只有一个含义：下一步该谁动（orchestrator，2026-09-16）。** 我第一版 SPEC §7 把它写岔了：承诺类按"谁欠"写（`promise`+`mine` = 我答应的），提问类却按"谁问的"写（说"对方问了我而我没回"是 `question`+`theirs`）。同一个字段两套读法，必然出事。提示词 v9 第 90 行和 ARCHITECTURE §2.5 一直写的是"谁欠下一步"，所以是 SPEC 错，已改：**对方问了我而我没回 = `question` + `mine`**（欠回答的是我）。种子数据按错的那版写了，一并改。

- **I11 `loops.text` 存不带主语的片段，句子在渲染时拼（orchestrator，2026-09-16）。** 提示词要求 `text` 不写主语（"周五前把报价发过来"），主语和动词由 `direction` + `kind` 在 `lib/loop-text.ts` 的 `loopSentence` 拼出来（"你答应…"、"她问你…，你没回"）。这样改措辞是改渲染，不用重新抽取。import-result 先按这个实现了，interaction 的人物页却直接打印原文加个句号 —— 同一条事项在两个页面读起来不一样。收进 `lib/loop-text.ts` 共享，两边都用它。种子数据存的是已经拼好的句子，再过一遍渲染会变成"你答应你答应帮她表妹看简历"，已让 verify-seed 改回片段并加单元测试把种子钉在同一条措辞规则上。

- **I12 反序导入不收敛（orchestrator，2026-09-16）。** SPEC M7 原本写"把两份记录反序导入，结果一致"。我按这条写了验收测试，结果是**不成立**：抽取只对新消息的窗口生成任务，先导晚的那份时那句了结的话就已经被读过了，等后来导入早的那份、loop 才被建出来，那句话不会再被重读；§8.4 的上下文消息也救不了，因为只落在上下文上的条目会被 `context_only` 丢掉。

  要自动收敛，只能在每新建一个 loop 之后，把它之后所有已读窗口重跑一遍找 `closes`，模型调用翻倍，v1 不值。用户手上有出路：人物页上点"已经了结了"。SPEC M7 已改成如实描述，`tests/integration/m7-interaction.test.ts` 第三个用例断言的是**真实行为**而不是愿望，并在注释里写明原因 —— 这样以后有人真去实现重跑，这条测试会以"失败"的方式提醒他改断言，而不是默默通过。

  值得记一笔的是：loop 的事件溯源设计本身是对的，前两条（正序关闭、删除导入后重新打开）都直接通过了，代价只出在"重读"这一件事上。


- **I13 `loopFalseClose = 0` 这个闸门我第一版定错了（orchestrator，2026-09-16）。** ARCHITECTURE §7.4 原文说它"只管机械错误"，但按字面实现出来，模型关掉了一条金标准认为还开着的事项也会计入 —— 一个诚实的判断失误就让整个 source 挂掉。eval builder 按规格实现了并如实提了风险，是对的。已改定义：`loopFalseClose` **只**统计机械上不可能的关闭（关的 loop 根本没给过这个窗口，或者关闭证据不在开启证据之后），这两种 `validateOutput` 已经拦掉了，所以还能漏出来就是管线或 harness 的 bug，闸门保持 0。模型把不该关的关了，算 loop 的假阳性，归 0.80 精确率那道闸，不归这里。

- **I14 离线结果的字段名必须钉死（orchestrator，2026-09-16）。** extract 产出 `segments[].participants` 和 `loops[].closedIdx`，eval harness 读的是 `speakers` 和 `closedByIdx` —— 两边对不上，而且**不会报错，只会安静地把所有交互指标算成 0**。这是最坏的一类 bug：指标全绿，其实什么都没测。已把 `memoryStore` 真实返回的形状写进 ARCHITECTURE §6，并让 eval 按这个形状读、加一个 fixture 断言把字段名钉住，让以后的改名以测试失败的形式暴露出来。

  **不能用"分流规则"解释掉。** harness 自带的 `分流 check` 提示说"claims 条数下降 + segments/loops 上升 = 规则在起作用"。这次是反的：claims 条数**从 50 涨到 55**，精确率同时下降，事务类比例几乎翻倍。也就是说模型没有把即时协调分流出去，而是在原来的活儿上变粗糙了 —— 一次调用里塞进三件新任务（segment / loops / closes），挤掉了它做 claim 的注意力。

  这直接挑战 **I6**（"不加第二次模型调用"）。I6 当时的理由是 28 秒 per-request deadline 里没有第二次调用的余量 —— 那是成本论证，不是质量论证，而现在有了质量证据站在反面。下一步要在三条路里选：把 v9 的提示词收紧到不伤 claims；把交互层拆成第二次调用（要重新设计窗口预算）；或者维持 v8 做 claims、交互层作为独立的第二遍处理。这个选择需要产品主人拍板，不是我自己能定的取舍。

- **I16 交互层本身是能跑出东西的，但质量没有任何测量（orchestrator，2026-09-16）。** 别把 I15 读成"交互层不工作"。单看 `聊天记录_20260912_095501.zip`，离线管线实打实产出 5 个段落、12 条未结事项、3 条关闭，字段齐整（`openedIdx`/`closedIdx`/`loopIndex` 都对）。但是：

  2. **harness 有两处上报缺陷，会让人误以为模型什么都没产出。** 报告里 `loops.predicted = 0`（真实是 12）、`conversationsPredicted = 0`（真实有 22 个段落可分组）。前者是"没有金标准就不计预测数"，后者是分组没跑。两者都不影响闸门，但都在**往"没产出"的方向撒谎**，正是 I14 那类错误的翻版 —— 指标好看/难看都不要紧，不能骗人。已记为待修。

- **I17 交互层拆成第二次调用，并行发（orchestrator + 产品主人，2026-09-16）。** I15 给出的证据面前，产品主人选了"拆"。具体：

  - **`extract.v9` 退役，不上线。** `PROMPT_VERSION` 回到 `extract.v8` —— 它今天现场实录过，合成样本闸门零项失败，是有测量支撑的选择，不是退回一个没测过的旧版本。
  - **新增 `prompts/interaction.v1.md` 与 `INTERACTION_PROMPT_VERSION`**，独立的 `InteractionOutputSchema`（contracts）。
  - **两次调用并行**（`Promise.all`），不是串行。交互调用不需要抽取调用的结果，所以窗口墙上时间是 `max(两者)`，28 秒预算不用重新谈。
  - **交互调用的输入更小**：不给已确认 claim 列表（它用不上），只给窗口消息、人物 label、上次来往、未结事项。成本增加远不到翻倍。
  - **失败各自隔离**：交互调用失败和 dedup 失败同级，非致命 —— 窗口照常 `done`，claims 照常入库，只记 `WindowOutcome.interaction = 'failed'`。反过来不成立：抽取调用失败，整个窗口重试，那一次的交互结果一起丢弃。

  这条明确推翻 **I6**。I6 说"不加第二次调用"，理由是 28 秒 per-request deadline 里没余量 —— 那是**延迟论证**。现在有**质量证据**指向反面，而且并行发之后延迟论证本身也不成立了。把这段留在这里，是为了让以后想合并回一次调用的人先看到这次的数字。

- **I18 盲标 annotator 找出的规格缺陷（orchestrator，2026-09-16）。** 它按 SPEC 标了 39 条 loop / 61 段会话，同时报回一份问题清单。逐条处理：

  1. **已修：§8.7「即时协调两边都不记」与 §7「约好但还没发生的事 = plan」直接打架。** "下周四晚上吃饭？"两条都占。采纳 annotator 的解法，按**时态**划界写进 §8.8：指向将来场合的是 `plan`，说当下的（"我到了""几点放学"）哪边都不记。并写明金标准里 `coordination` 反例**只约束 claim 不约束 loop** —— 不写这一句，交互提示词会照旧措辞把语料里所有约饭都压掉。
  2. **待定（需产品主人拍板）：四种 kind 装不下「没人认领的请求」。** "请各位家长把紧急联系人信息私发给我"、"你们谁有空帮我问问租金" —— 没人承诺、没有约定、也未必是疑问句，但用户确实欠着。annotator 说这是**真实群聊里最常见的一种**，现在无处安放。要么加第四种 `kind: 'request'`，要么归到 `question` + `mine`（语义别扭，界面标签"问题"不对）。
  3. **待定：`direction` 在「第三方自己的计划」上失效。** "我四月底搬去深圳" —— 谁也不欠谁。`theirs` 是最不坏的选择，但渲染出来会变成"他答应…"，是错的。要么加第四种 direction，要么让 `plan` 允许没有归属方。
  4. **已确认是设计使然，不是缺口：窗口内开闭的事项抽不出来。** `closes` 只能引用**上一个窗口**带进来的 loop id；而 §8.8 本来就规定"片段里已经被回答、被做到、被取消的，不是未结事项"——所以这类东西根本不该成为 loop。annotator 独立地得出了同一条规则并据此排除了若干诱人的开闭对，这是个好信号（规则是可推导的，不是拍脑袋的）。**但后果要记住**：39 条 gold loop 里只有 7 条带 `closedBy`，有一份样本一条都没有，所以 `loopCloseRecall` 头几轮是个样本极小、方差极大的数，不能当成稳定指标读。
  5. **已知：问题类永远没有关闭路径。** §8.7 说被回答的提问就不是未结事项，所以 question 只能生而未结。逻辑自洽，代价是 `closedReason: 'done'` 只对 promise 和 plan 可达。
  6. **重要：真实聊天几乎产不出 loop。** 三份真实导出一共 4 条（其中一条还是选颜色）。也就是说 loop 的闸门**实际上是在合成数据上测的**，真实样本那道 `precisionLenient ≥ 0.80` 可能由一两条决定。定闸门时必须知道这件事。
  7. **已知：群聊 loop 挂谁身上往往是任意的。** 一个家庭计划，提议的和确认的不是同一个人，挂哪边都说得通；而 loop 匹配要求 person key 相等，于是这会变成一种**沉默的漏检**，报告里任何字段都解释不了。

- **I19 annotator 拒绝了一条 intent 分歧并留下警告（orchestrator，2026-09-16）。** `loop-book-room` planted 的那条在**同一个窗口里**开启又被推翻，按上面第 4 条管线根本表达不了，所以它没有采纳，把警告留着，并说明这是生成器与 §8.5 的冲突、该由 eval-synthetic 定夺，不是金标准的错。这是正确做法：金标准不该为了消掉一条警告而收录管线不可能达到的条目（那是在制造无法达成的召回）。另外 3 条分歧它复读原文后采纳了。
